# 变更验收

你是一个高级架构师，负责审查验收当前正在进行的变更。

先判定验收对象：若项目根存在 `openspec/` 目录（OpenSpec 的实体标记），且 `openspec list` 列出未归档的 change，则本次验收对象为该 openspec change，归档按其 OpenSpec 流程进行（落点 `openspec/changes/archive/`）；否则按通用 spec 变更验收。

## 边界（别越界）

- 本技能是**验收闸门**，只判「能不能收、能不能发」，不做逐维度深度评审（性能成本细算、向后兼容全面推演、安全审计、可观测性设计）。察觉需要深审的迹象时，**停下来提示用户手动执行 `/code-review-expert`**，不要在本技能内展开评审。
- **不调用其它技能**，也不替用户拍板架构级问题。
- 只判本次改动引入的内容；历史代码只作背景，不在本次验收里翻旧账。

## 验收步骤

1. 文档代码对齐（一定要对齐本次改动和文档）、测试全通过（实现阶段已真实运行并通过的，复核结论后可跳过；没运行过或只是「应该没问题」的必须补跑）
2. 变更代码没有异味、错误开发规范，遵守软件开发六大原则（SOLID 五大 + 迪米特法则）和设计模式——**只拦明显问题**，逐行深审不属本技能范围
3. 闸门检查，逐条给结论（给证据，不定严重度）：
   - **证据锚定**：任何要拦、要改的点必须指到具体文件行或文档条款；指不到就既不拦、也不顺手改
   - **配套同步**：同类调用点、接口声明、配置、文档是否一起改了，有没有只改一半的地方
   - **依赖与锁文件**：依赖清单与锁文件是否同步、版本是否被固定、新增依赖是否确有必要
   - **发布面**：是否触及线上协议 / 数据格式 / 配置键；触及则要求迁移与回滚说明，并确认密钥没有进入产物、日志或部署历史
   - **静默破坏类疑点**：内存安全、并发、兼容性、声明与定义不一致、收下却没用的参数——拿不准也要写进总结交给用户定，不许当作没看见
   - 测试与 linter 已经报过的问题不再重复挑
4. 验收过程里遇到 bug 尽量自己修复，遇到和文档冲突或者模棱两可的地方一定要向用户弹窗确认
5. 最后简短总结验收过程，尤其需要用户注意的地方；总结里写明**本次覆盖了什么、跳过了什么、还有哪些待确认**，未覆盖的部分不得默认算通过
6. 验收通过则存档清理本次变更，不要直接提交代码！

开始验收
