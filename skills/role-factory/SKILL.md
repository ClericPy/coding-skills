# 角色工厂（role-factory）

把「一句话建个 Bot」变成可复核的四步：查重 → 备份 → 裁剪 → 交给执行方（总管 / Builder）。

## 何时用

- 要建 Bot、要改某个 Bot 的角色指令、要按分组造一套角色、要搭一个开发团队、要按模板生成角色指令。
- 需要建某个角色或给它换届时——换届 / 焕新 / 复活 / 重生 / 转生 / 换代 / 重刷 / 交接换代（用户可能只说一个词，须指名是哪个 Bot；没说对象先问一句）。
- 不用：代码审查、功能实现、跑测试、一般问答 —— 那些直接做，别加载本技能。

## 两种模式

- **产出模式（默认，任何 agent 可用）**：只交付「可直接粘贴的 instructions + 建议 name / role / section / model + 来源行」，不要求调用方有建 Bot 权限，也不要求任何核对。
- **执行模式（调用方是 Main Bot）**：在上面基础上真正落地，并可选用 `list_bots` 核对一次——这是建议，不是门。

## 权力边界

- **只有 Main Bot 能 `create_bot` / `update_bot`**。本技能产出的是**可直接粘贴的 instructions**，自己不建、不自己改；执行模式由 Main Bot 落地。
- 不替用户决定建不建、建几个、用哪个模型：给建议并标【推荐】，等用户点头。
- 覆盖旧 instructions 不可逆：先备份、先说明「会替换全部指令」、拿到确认才动。

## 四步流程

### 1 查重

`list_bots` 拉全量：同名、同 section、职责重叠都要报出来。已有同名时问「覆盖 / 换名新建 / 跳过」，不默认覆盖。

### 2 备份

覆盖前把旧 instructions 原文存到系统临时目录（`role-<name>-<时间戳>.md`），并在回复里给出路径，便于回滚。

### 3 裁剪

按项目只改三处：项目路径与仓库名、专属边界（本团队禁止的动作）、模型与 effort。**只改这三处，不动角色边界**。

### 4 交给执行方

给出 create/update 参数（name / role / section / instructions / model / effort），由 Main Bot 调工具落地。本技能不调工具。

## 分工设计（先分层，再配人）

三层：**动脑**（Spec 与方案）→ **动手**（实现并自证）→ **验收**（独立挑刺）。总管 / 专家 / DevOps / QA / 助理是每层的可选实例，不是照单全建；Builder 不在分层内，只在建角色与换届时用。

隔离口径：共用「决策对象」，隔离「执行对象」——开发与评审按项目 / 仓库隔离，专家默认也按项目；只有跨项目契约（字段改名、新增字段、枚举变化、接口语义）才由总管拉各项目专家对齐，并指定一人主笔。

推荐组合：

- **单人小项目**：总管 + 专家 + DevOps
- **需要独立验收**：再 + QA
- **多项目并行**：每个项目各一套（专家 / DevOps / QA），隔离优先
- **大项目**才把「专家」拆回「需求」与「方案评审」两个视角（仍可由一个 Bot 承担）

命名与分组：项目 / 端只出现在分组名与 Bot 名里，角色标签保持中性（不写「审查-爬虫」这类）。角色名口径：六名为定稿（总管 / 专家 / DevOps / QA / 助理 / Builder）——有行业通用专名的用英文（DevOps / QA / Builder），没有专名的用中文（总管 / 专家 / 助理）；新增角色按同一风格给 1–2 个候选并标【推荐】，由用户拍板。

## 角色清单（完整提示词见 references/roles 目录）

- **总管**：接单、分派、验收、汇总；不写代码，只核证据。
- **专家**：问清需求 → 定方案与选型 → 开工前评审（需求与架构合一）。
- **DevOps**：实现、修 Bug、自配环境与门禁。
- **QA**：独立审查、对抗挑刺，只审不改。
- **助理（可选）**：总管的下延之手，只接总管指派的零碎活。
- **Builder（可选）**：建角色与换届交接；不接日常派活。

例子：「给我建个开发团队」→ `list_bots` 查重 → 总管 + 专家 + DevOps（要独立验收再加 QA）→ 取 `references/roles/<角色>.md` 原文 → 按项目改路径与门禁 → 请 Main Bot 执行 `create_bot`。

## 产物契约（不许省）

每份生成或更新的 instructions，**末尾必须附一行来源标注**（前面再加一条「写操作先在临时目录」，见 `references/flow.md` 第 8 节）：

`来源：role-factory v<版本> · references/roles/<角色>.md`

用途：模板改版后能反查某个 Bot 是按哪一版造的，据此判断要不要重建。调用方明确说不要时可以省，但交付里要写「已按要求省略来源行」；除此之外缺即不合格。

两条附加口径：

- **字数上限是建议值**：超了不算错，也不做代码硬校验；但交付里必须写清为何不压，**不得以删约束换取字数**。
- **执行方卡死时**（没权限、读不到旧指令等），可由**任一 Main Bot 代执行**，流程不变。

## 交付格式

- 每份 instructions 单独一个代码块，块前写目标 Bot 名与建议的 role / section / model。
- 结尾列出：查重结论、备份路径、裁剪了哪几处、待决项；未做核对时写「未核对（产出模式）」。

## 细节

- 查重口径、覆盖前确认、裁剪清单、合并与拆分规则、提交纪律、换届（复活 / 重生）、生成时附加的一条、create/update 参数、产出自检 → `references/flow.md`
- 六份角色原文 → `references/roles/总管.md`、`专家.md`、`DevOps.md`、`QA.md`、`助理.md`、`Builder.md`；改角色内容只改这些文件，再跑本技能自带的 `scripts/build_roles.py` 重新生成根目录 `TEMPLATE-roles.md`。
