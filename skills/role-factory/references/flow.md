# 落地流程（role-factory）

## 0 两种模式

- **产出模式（默认，任何 agent 可用）**：只交付「可直接粘贴的 instructions + 建议 name / role / section / model + 来源行」。不要求调用方有建 Bot 权限，也不要求任何核对。
- **执行模式（调用方是 Main Bot）**：在上面基础上真正落地，可选做第 10 步的核对。

## 1 查重

- `list_bots` 拉全量，报三类：同名、同 section、职责与其他 Bot 重叠。
- 已有同名 → 问「覆盖 / 换名新建 / 跳过」，默认跳过，不默认覆盖。
- 同 section 已有人 → 说明职责差异，问是并行还是合并。

## 2 覆盖前三件事

1. **备份（主路径）**：读 `state.json` 的 `bots[].instructions`，把旧指令原文存成 `role-<name>-<时间戳>.md` 放系统临时目录，回复里给路径。
2. **说明**：明确写「覆盖会替换全部指令，不是追加」。
3. **确认**：用户从「覆盖 / 新建 / 跳过」里选一个，没选不动。

## 3 裁剪清单

只改这三处：

- 项目路径与仓库名（把模板里的泛称换成真实仓库）。
- 专属边界：本团队禁止的动作、必跑的门禁命令、发布面约束。
- 模型与 effort（按任务复杂度给建议）。

不动：角色职责、硬边界编号、检查清单结构。

## 4 合并与拆分规则

- **默认合一**：专家一节同时管需求与架构（需求 → 方案 → 评审），省一次交接。
- 需要拆时（Review 要更快、或需求调研与方案评审节奏差很远），拆成「需求」与「方案评审」两个 Bot；拆的代价是两套输入都要读（需求 + 代码 / 既有实现），要在交付里说明。
- **产出方与验收方绝不可合**：自己写、自己审、自己通过，等于没有验收。

## 5 提交纪律（先评审 PASS 再提交，不新增角色）

1. 开发改完**不提交**：只跑门禁，留命令原文与输出。
2. 评审审**未提交的 diff + 本次门禁输出**，不看已提交的历史。
3. **PASS 之后开发才提交**：按 `/ccccc` 规范（前缀只用固定词、粒度宁粗勿碎、单次新增 >500 行在 Body 说明「为何不拆」、只做普通提交、不 push、不 force）；`/ccccc` 未安装时按仓库既有约定，并在交付里注明「未按 ccccc 规范」。
4. 推送前由总管核证据，并在账本先记一行（目标分支、提交 hash、证据指针、时间、结果）；推送后核对远端回执再销账。push 是本流程唯一不可逆点：先记账本，再动手。

## 6 换届（复活 / 重生）

- **触发词**：换届、焕新、复活、重生、转生、换代、重刷、交接换代。必须指名对象（如「给 coding-skills 的 QA 换届」「把总管复活」）；只说词不说对象时先问一句，别乱动。
- **为什么**：会话过长会变慢（上下文每轮重发、折叠会丢细节）。换届 = 保住记忆与交接，换一个新会话。
- **流程**（一份清单，不拆两份）：
  1. **腾名字**：旧身自己做，或 BotBuilder 用 `update_bot` 代做（如改成 `退休·总管`）；名字全队唯一——改名撞名报 `Name 总管 is not available`（`roster.js:415`），建新身撞名报 `A Bot named 总管 already exists`（`roster.js:188`）。**改名仍然必须做**：挪分组不释放名字；随后把旧身挪进「待下线」分组（`update_bot` 的 `section`），不留在原分组。
  2. **建新身**：`create_bot`（指令抄旧身原文），并搬主题记忆文件（`MEMORY.md` 与主题 md 直接拷进新身记忆目录）——工具**没有 `main` 参数**，Main 身份只能用户在 GUI 给。
  3. **交接摘要由旧身写**（BotBuilder 不编内容——它不知道对方在做什么）：在做的、最近刚做完的、待授权项、当前仓库 HEAD 与未推提交。**不要另写「精华条目」**：与被交接方原有条目近义不重合，机械删会丢边界。
  4. **收尾**：用户在 GUI 把新身设为 Main（可替换旧身，接口支持 `primary` / `replace`；两个 Main 并存的过渡期正常，交接没完成别急着撤）→ 撤旧身 Main（只有用户能做）→ 用户单独发话后，由**用户在 GUI** 删掉待下线里的旧身；Bot 侧没有删除工具。
- **会话卡或过大**：≥2 MB 先建议「重启（= 新起一段）」——首选让用户在 GUI 用「新起一段」（同一个 Bot、指令与记忆不动，旧 part 仍可读；只限 Bot 自己的 chat，正在干活时先 `stop_bot` 或等它做完）；`≥4 MB`、用户主观觉得卡、或要换指令 / 换模型 / 彻底重来 / 删旧身，才走换届四步。阈值与体检口径见 §7。
- **红线**：新身不是 Main 时不能建/改角色；总管这类还要 `stop_bot`（同样只有 Main 能用），所以**总管与 BotBuilder（`references/roles/BotBuilder.md`）都必须留 Main**，不能只留一个。

## 7 会话体检（仅 DSH）

- **只在 DSH 有意义**：读 `~/.dsh/bot/state.json` 的 `bots` 拿 id 与 name，再按 bot id 匹配 `~/.dsh/sessions/<工作目录 slug>/session-<uuid>/session*.jsonl.zstd` 的体积。没有这两处路径的 harness 直接跳过并说明「本环境不支持体检」——不猜、不自造指标。
- **只读**：不改会话文件、不解压、不删任何东西。
- **不要试图数轮次**：node 内置 `zstdDecompressSync` 只能解第一帧，读到的是会话头；体积够用，别为此装新工具。
- **阈值是经验值，不是测量结论**：`≥2 MB` 建议重启——`2–4 MB` 首选 GUI「新起一段」（同 Bot、记忆不动、成本低），`≥4 MB` 或用户主观觉得卡才建议换届。参考锚点：干净会话 0.07–0.64 MB，1.1–2.4 MB 开始有感，6.36 MB / 400+ 轮在 GUI 上明显卡。
- **何时跑**：只在用户说「看下谁卡了 / 谁的会话太大 / 该不该换届」，或被总管点名时跑；**不设定时巡检**，也不没人让就主动体检。理由：单次判断再准也会累积误差——单次 99% 准确、一天 288 轮至少错一次的概率是 1−0.99^288 ≈ 94.5%，所以只做按需的一次判断，不换成轮询保新鲜。

## 8 create/update 参数

| 参数 | 怎么给 |
| --- | --- |
| `name` | 英文短名，全团队唯一；中文名放 `role` 或用作显示名 |
| `role` | 用口径名（总管 / 专家 / DevOps / QA / 助理 / BotBuilder），2–10 个字符 |
| `section` | 分组名；同项目团队放同一 section |
| `instructions` | 整段原文（临时目录那条 + 来源行已附），不做改写 |
| `model` / `effort` | 给建议值并说明理由，不替用户定 |

新建用 `create_bot`；改已有 Bot 用 `update_bot`（`bot` + 新 `instructions`）。

## 9 生成时附加的一条（写操作先在临时目录）

角色节里不重复这条，由本技能在生成时填到 instructions 末尾（来源行之前）：

```
写操作先在临时目录试（一次性脚本、临时文件落系统临时目录，用完即删）；不改仓库已跟踪文件。
```

## 10 产出自检（建议，不是门）

- 调用方本身有建/改权限时，**建议**用 `list_bots` 核对 name / role / section / model，并确认 instructions 末尾有临时目录那条与来源行。
- **核对不上如实报一句即可**，不算失败、不阻塞交付。
- **能脚本判的不写进指令**：`TEMPLATE-roles.md` 与角色源一致由 `scripts/validate.py` 覆盖（frontmatter 取值与长度、引用文件存在性、SKILL 正文行数同理）；指令只写脚本判不了的部分（谁、何时、怎么取舍）。`TEMPLATE-AGENTS.md` ↔ `~/.dsh/AGENTS.md` 逐字节一致是人工核对项——validate 并不查它。新增规则先问「能不能写成一条检查」，能就进脚本。
- 没有权限或不需要核对 → 跳过，交付里写「未核对（产出模式）」。

## 11 来源行

- 默认附：`来源：role-factory v<版本> · references/roles/<角色>.md`
- 调用方明确说不要 → 可以省，但交付里要写「已按要求省略来源行」。
- 这一行是给未来反查用的：模板改版后能判断某个 Bot 是按哪一版造的。
