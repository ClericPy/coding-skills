# 落地流程（role-factory）

## 0 两种模式

- **产出模式（默认，任何 agent 可用）**：只交付「可直接粘贴的 instructions + 建议 name / role / section / model + 来源行」。不要求调用方有建 Bot 权限，也不要求任何核对。
- **执行模式（调用方是 Main Bot）**：在上面基础上真正落地，可选做第 8 步的核对。

## 1 查重

- `list_bots` 拉全量，报三类：同名、同 section、职责与其他 Bot 重叠。
- 已有同名 → 问「覆盖 / 换名新建 / 跳过」，默认跳过，不默认覆盖。
- 同 section 已有人 → 说明职责差异，问是并行还是合并。

## 2 覆盖前三件事

1. **备份（主路径）**：读 `state.json` 的 `bots[].instructions`，把旧指令原文存成 `role-<name>-<时间戳>.md` 放系统临时目录，回复里给路径。
2. **说明**：明确写「覆盖会替换全部指令，不是追加」。
3. **确认**：用户从「覆盖 / 新建 / 跳过」里选一个，没选不动。

## 3 裁剪清单

只改这三处：

- 项目路径与仓库名（把模板里的泛称换成真实仓库）。
- 专属边界：本团队禁止的动作、必跑的门禁命令、发布面约束。
- 模型与 effort（按任务复杂度给建议）。

不动：角色职责、硬边界编号、检查清单结构。

## 4 合并与拆分规则

- **默认合一**：专家一节同时管需求与架构（需求 → 方案 → 评审），省一次交接。
- 需要拆时（Review 要更快、或需求调研与方案评审节奏差很远），拆成「需求」与「方案评审」两个 Bot；拆的代价是两套输入都要读（需求 + 代码 / 既有实现），要在交付里说明。
- **产出方与验收方绝不可合**：自己写、自己审、自己通过，等于没有验收。

## 5 提交纪律（先评审 PASS 再提交，不新增角色）

1. 开发改完**不提交**：只跑门禁，留命令原文与输出。
2. 评审审**未提交的 diff + 本次门禁输出**，不看已提交的历史。
3. **PASS 之后开发才提交**：按 `/ccccc` 规范（前缀只用固定词、粒度宁粗勿碎、单次新增 >500 行在 Body 说明「为何不拆」、只做普通提交、不 push、不 force）；`/ccccc` 未安装时按仓库既有约定，并在交付里注明「未按 ccccc 规范」。
4. 推送前由总管核证据。

## 6 create/update 参数

| 参数 | 怎么给 |
| --- | --- |
| `name` | 英文短名，全团队唯一；中文名放 `role` 或用作显示名 |
| `role` | 二到四字标签，如「总管」「开发」 |
| `section` | 分组名；同项目团队放同一 section |
| `instructions` | 整段原文（临时目录那条 + 来源行已附），不做改写 |
| `model` / `effort` | 给建议值并说明理由，不替用户定 |

新建用 `create_bot`；改已有 Bot 用 `update_bot`（`bot` + 新 `instructions`）。

## 7 生成时附加的一条（写操作先在临时目录）

角色节里不重复这条，由本技能在生成时填到 instructions 末尾（来源行之前）：

```
写操作先在临时目录试（一次性脚本、临时文件落系统临时目录，用完即删）；不改仓库已跟踪文件。
```

## 8 产出自检（建议，不是门）

- 调用方本身有建/改权限时，**建议**用 `list_bots` 核对 name / role / section / model，并确认 instructions 末尾有临时目录那条与来源行。
- **核对不上如实报一句即可**，不算失败、不阻塞交付。
- 没有权限或不需要核对 → 跳过，交付里写「未核对（产出模式）」。

## 9 来源行

- 默认附：`来源：role-factory v<版本> · references/roles/<角色>.md`
- 调用方明确说不要 → 可以省，但交付里要写「已按要求省略来源行」。
- 这一行是给未来反查用的：模板改版后能判断某个 Bot 是按哪一版造的。
