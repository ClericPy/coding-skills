# 规范化 Git 提交

回顾最近 5 次提交信息，学习提交格式：

1. 公司要求的提交格式非常严格，要注意冒号左边就那几个特定单词、空格空行都要一一对应。（fix:/feat:/docs:/test: 等）
2. 如果模板里有 ID 类的字段（例如 JIRA-ID），用户没有指定，就用最近一次的那个 ID，绝不凭空构造；其他字段不确定也不要凭空捏造，只要其他几次提交都用了那个值，就继续复用那个值；但 ID 的复用仅限同一分支 / 同一需求范围内，跨需求时必须先向用户确认，绝不沿用旧单号
3. 要自动根据上下文判断现在准备提交的是在 worktree 里还是正常分支上
4. 提交完成后汇报改动行数情况，并打印告诉用户提交信息填的什么
5. 注意 description 不要太长，200 字以内，绝对不要换行，多条可以用；隔开
6. 调用本技能即视为授权创建提交：直接提交，不必再向用户确认；提交前检查暂存内容，发现密钥等敏感信息或明显无关文件时停下询问；但绝对不要 push
7. 单次 commit 新增超过 500 行时，须在 Body 写明为何不拆（写进已有的描述行，不新增行，见规则 9）。**超过 500 行本身不构成拆的理由**：拆不拆由规则 8 判；拆时粒度取「可独立 review 的单元」，不按文件或按步骤机械拆
8. 粒度宁粗勿碎：同一需求 / 同一主题的小改动（含沾边的文档、配置、测试同步）合成一次提交，判据是 reviewer 能否一次看懂，不是行数；默认「一个需求一次提交」，只有互不相干的主题、或需要单独回滚的部分才拆开
9. 除了提交信息里有的那些行，绝对不要自己加新行放太多冗余信息，可以在描述里单行描述代替新增行

## 样例

**ID 复用边界**（规则 2 只说了「同一分支 / 同一需求可复用」，怎么判「同一需求」需要对照）：

```text
最近提交：feat: PROJ-884 导出任务支持重试
          fix: PROJ-884 重试次数上限修正
本次：仍在同一分支，内容仍是导出重试这件事，用户没给单号
→ 复用 PROJ-884，不必问（同一需求范围内）

本次：分支已切到 export-v2，内容是全新的导出格式，用户没给单号
→ 停下来问：「这属于新需求，沿用 PROJ-884 还是开新单号？」（跨需求不得沿用）
```

**超 500 行但同主题**（规则 7 只要求说明，拆不拆看规则 8）：

```text
本次：620 行，全部属于「导出重试」同一主题，拆开后任一条都无法单独 review
→ 一次提交，Body 写明：本次 620 行 / 同主题 / 拆开会把重试状态机切成两段，故不拆。

反例：把同一主题拆成「重试上限 + 状态机」两条提交——后一条单独读不出重试上限的上下文，
不满足规则 7 的「可独立 review 的单元」，也不满足规则 8 的拆分触发条件（同主题、无需单独回滚）。
```

## 输出语言

提交信息语言跟随最近 5 次提交的惯例（含字段与 ID 写法），不随对话语言变化。
