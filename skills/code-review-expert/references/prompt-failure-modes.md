# 提示词文档评审：判据与故障模式

本文件给 `code-review-expert` 的文档类评审提供判据。评审对象是**给模型执行的指令**，不是文章：写得漂亮但模型照做会出错，就是 Blocker。

判据分两组：**T1–T7 看文本**（矛盾、简练、冗余、抽象名词、逻辑、不可判定、层级），**P8–P15 看它能不能正常工作**（触发、优先级、可执行、上下文预算、负面指令、示例一致、关键约束位置、事实真实性）。

## 读法与分工

- 第 4 步（逐判据过筛）读 T1–T7；第 5 步（提示词侧专项）读 P8–P15。
- 每条判据都要求能判真假：判据 → **判法**（拿什么事实去判）→ 典型故障模式 → 改法要求。判不出真假的问题不报，改法给不出具体内容的不报。
- 层级错位的细则只在 T7 定义，P11 不重复。
- 与七维度的分工：代码质量、脚本实现、依赖与构建配置一律不在本文件范围，走 `/change-linter`、项目原生工具链或代码侧七维度。

## 文本判据 T1–T7

### T1 前后矛盾

**判据**：同一件事在全文中出现 N 次时，每处的结论必须一致；规则与示例、主规则与例外条款也必须一致。

**判法**：拿第 2 步建的条目索引，按「讨论的对象」归并（不是按章节），同一对象的条目逐对比较，每对给一个判定：一致 / 矛盾 / 分层（分层归 P9 判）。

**故障模式**：主规则说 A、示例说 B；两节各定义一份同一件事的判据；正文说「只写判断规则」，后文又列一堆机械细节；改了一处没改引用它的另一处。

**改法要求**：指明保留哪一处、另一处删除或改为指针；若是例外关系，补「本条覆写 X」的声明（见 P9）。

### T2 不简练

**判据**：存在「删掉之后结论不变」的字句。

**判法**：逐句做删除测试——删掉该修饰语 / 从句后，结论是否反转或丢失限定？不反转即可删。**举例单独处理**：装饰性例子可删；若该例子是这条规则唯一的可执行规格（规则本身不可判定，见 T6），则不删，转 T6 处理——**举例的去留以 P13 为准**。给出的报告必须含「删 X 字 → 原句变为 Y」。

**故障模式**：过程叙述（「我们先……然后……」）；口语化修饰（其实、非常、值得注意的是、总之）；能用表格却写成并列长句；把理由写成散文段落。

**改法要求**：给出删改后的原句。**限定词（不 / 禁 / 仅 / 除非）不算修饰语**，删前必须确认语义不反转（与 T5 联动）。

### T3 冗余

**判据**：同一规则或同一判断在两处**定义**（换词重说、限定语与主句重复）。

**判法**：索引里同一对象出现 ≥2 次时，区分「定义」与「引用」——出现「见 §X」的算引用，不算冗余。两条规则若指向不同侧面（能被同时违反且后果不同），按 `templates/AGENTS.md` §1「同一规则只定义一处」不算重复。

**故障模式**：同一规则换个说法再写一遍；限定语与主句说同一件事；两个章节各写一份「自检覆盖」。

**改法要求**：给出两处原文行号，明确保留哪一处（通常是更细或裁决点那处），另一处改为指针。

### T4 专业名词罩住一大段

**判据**：用抽象名词替代具体判据，读者无法据此判断真假。

**判法**：把该词替换成问句——「这条规则被违反时，我能指出具体哪个行为吗？」指不出即判据不成立。高频词：合理、健壮、优雅、充分、适当、正确处理、按最佳实践、遵循规范、尽量、注意。

**故障模式**：「做适当的错误处理」「遵循项目最佳实践」「保证代码健壮」。

**改法要求**：补成可判定条件（阈值、允许 / 禁止清单、检查命令），或给一个正反例，或下沉到 references 并写明领域来源。

### T5 前言不搭后语 / 逻辑断裂

**判据**：缺前提条件、因果倒置、限定词丢失、触发词与规则对不上、按字面执行会失败。

**判法**：逐条问三个问题——(a) 执行它需要先满足什么，文中给了吗？(b) 因果链方向对吗？(c) 把否定词去掉，语义是否反转（是则该词是关键约束，排版与措辞都要保护）。

**故障模式**：要求「改完必须跑 X」却没说 X 不存在时怎么办（缺出口，见 P12）；「因为 A 所以 B」而 A 其实是 B 的结果；触发词表漏列实际会出现的字符；条目顺序让读者先做后一步。

**改法要求**：补前提、调整顺序、补限定词或补出口动作。

### T6 不可判定

**判据**：规则既无法机械判真假，也没有例子、判据出处或阈值。

**判法**：拿规则去判三个假设场景，如果三次都能得出「看情况」，即判据不成立。

**故障模式**：「代码应当清晰」「文档要保持一致」「必要时补充说明」。

**改法要求**：三选一——补判据（阈值 / 清单）、给例子、下沉 references 并注明领域依据；三者都不成立就建议删。

### T7 层级错位

**判据**：按 `CONTRIBUTING.md` 的三层加载表判断内容该在哪一层——常驻层（`description`）、正文层（`SKILL.md`，>500 行有警告）、第 3 层（`references/`、`scripts/`）。

**判法**：对每段问「模型在完成任务的哪一步需要它？」答案是「某一步、且篇幅超过 5 行」→ 该下沉；答案是「每次调用都要」→ 留正文。对非技能文档（AGENTS.md / CONTRIBUTING / README），等价判据是文档自己声明的定位（如「只写无法机械判定的判断规则」），正文与定位不符即层级错位。

**故障模式**：SKILL.md 正文里塞满只在某一步用的规则表；正文写了自带脚本的内部实现细节；全局规范里混进换机即失效的本机环境细节。

**改法要求**：指出下沉目标文件与在 SKILL.md 补的「何时读」指针（标注在流程第几步）。

## 提示词判据 P8–P15

> **先分清手动 / 自动技能，这是本文件最容易被用错的一处。**
> 带 `disable-model-invocation: true` 的技能（本仓多数：提交、终端、验收、本技能）**不靠 description 触发**——模型不会自己选，人是通过 `/` 菜单点名调用。拿自动技能的触发判法去评手动技能，会产出假 Blocker（「description 缺触发词」对手动技能根本不成立）。
> 因此 P8 拆成两套判法：自动技能判「模型是否会想起」，手动技能判「人能否一眼认出」并检查反向触发。用错整套判法的报告无效。

### P8 触发可靠性

**判据（自动技能，无 `disable-model-invocation`）**：description 必须含真实用户会用的触发词（中英双语更稳），并给出反向触发（`不用于 X，改用 Y`）。

**判法（自动技能）**：把同仓所有 description 并列，对每条真实提问（从 `CHANGELOG`、用户历史取）列出会命中哪几个技能。命中 0 → 从不触发；命中 >1 且没有优先级说明 → 抢活。命中错了即 Blocker。

**判据（手动技能）**：description 首句能让人在 `/` 菜单里一眼认出用途；写明「仅限手动调用」；反向触发指路到正确技能。

**判法（手动技能）**：把 description 当菜单条目读——只看首句，能否判断「这件事该不该点它」？首句是「资深架构师级……融合……维度」这类自我描述而不含对象与用途的，判 Major。

**故障模式**：只说「适用于……」而无反向触发；触发词写的是内部术语而非用户口语；两个技能的 description 共用同一个动词（如「验收」「review」）而无分界。

**改法要求**：补触发词、补反向触发并写明改用谁、给冲突的一对加一句职责分界。

### P9 指令优先级与冲突

**判据**：多条「必须 / 禁止 / 绝不」并存时，冲突谁赢必须写清；与 harness 约束或 `templates/AGENTS.md` 冲突而技能未声明优先级的，视为技能不生效。

**判法**：候选冲突先分三类，再决定报不报——
1. **真矛盾**：同一对象、同一条件、不同结论，且没有一条声明覆写另一条；
2. **分层**：一条是通用规则、另一条是例外，**且例外条款显式写了「在什么条件下覆写谁」**；
3. **伪冲突**：两条管的是不同对象（例：「不评删除的行」与「删除导致新代码矛盾时要评」）。

**判定规则：例外条款没有显式覆写声明的一律按真矛盾处理。** 这是 P9 的核心：两条都在裁决同一件事、又都没说谁覆写谁，就是真矛盾。例：一条写「已放行的操作不再请示」，另一条写「破坏性命令必须先确认」，两句都没声明谁覆写谁——判真矛盾，改法是给后者补「本条覆写前者」。**样例一律匿名，不点具体文件、章节或技能**（与 P13 同一条纪律：判据不依赖会被修掉的具体缺陷；缺陷修掉后匿名样例仍然成立）。

**故障模式**：两个章节各自命令同一件事；例外条款只说「例外」不说覆写谁；技能要求的行为与平台约束（如「只读模式」「只出评论」）相悖却未提。

**改法要求**：给例外条款补「本条覆写 §X 的 Y 条」；或把两条合并成一条带条件的规则。

### P10 可执行性

**判据**：指令是祈使句（动作 + 对象 + 判定条件），并写清执行前要拿到什么、做完产出什么。

**判法**：把每条指令当工单派给不了解背景的人——他能否知道第一步做什么、拿什么、交什么？

**故障模式**：描述句当指令（「应该谨慎处理」「要注意兼容性」）；要求做某事却没说先拿到基线 / 工具输出；没有输出契约（做完给报告还是改文件、什么格式、给谁）。

**改法要求**：改成动作句；补输入前置与输出格式。

### P11 上下文预算

**判据**：常驻层与正文层不被迫承担别的层的信息；同段里模型真正要执行的句子占多数。

**判法**：给每段打标签——常驻需要 / 某一步需要 / 背下来没用。第三类占比超过三成判 Major。层级归属细则看 T7，这里不重复定义。

**故障模式**：description 里塞了本该在正文的完整流程；正文把说明书式的背景知识写成大段；同一件事先说一遍再举一遍再说一遍。

**改法要求**：下沉、删除或改为指针；`.md` 参考文件超过 300 行时补目录。

### P12 负面指令的有效性

**判据**：每条「不要 / 禁止 / 绝不」都给了替代动作。

**判法**：逐条问「那应该做什么？」，答不出即缺出口。

**故障模式**：只写「不要读源码」而不给 `--help`；只写「禁止臆造成果」而不给降级链；一个禁令覆盖多种错误行为却只给部分出口。

**改法要求**：补「不要 X，改用 Y」；多错误行为给一个统一出口动作。

### P13 示例与规则的一致性

**判据**：有示例的，逐个核对与规则一致；无示例的，判断该规则是否必须靠例子才能执行。

**判法**：把示例当输入，按规则模拟执行一遍，看结论是否与示例一致。不一致判 Blocker——示例是模型的首要模仿对象，规则与示例冲突时模型更可能抄示例。**与 T2 不冲突**：T2 管例子该不该留（装饰性可删），P13 管留下来的例子是否与规则一致。

**通用反例**（不带具体技能名，也不依赖本仓现状）：「某规则写『单次改动不超过 500 行，超过才拆』，下一行又写『判据是能否一次看懂，不是行数』」——示例无论写哪一边都会与另一边冲突。**评审判据本身不得依赖会被修掉的具体缺陷**，否则修完示例即过期。

**改法要求**：改示例或改规则，二选一并说明保留哪边；两者都要保留时，把其中一条明确降为例外并写清适用范围。

### P14 关键约束的位置

**判据**：前置条件、禁令、输出格式三类约束出现在显眼位置；硬约束不埋在长正文中段。

**判法**：统计三类约束的行号分布。落在全文 40%–70% 且没有节标题提示的，判 Major；建议抽成开头速览或提升为独立小节。

**故障模式**：红线在第 35–46 行的正文里、前面全是常规内容；输出格式只出现在末尾示例中；禁令散落在各节。

**改法要求**：抽到开头或提为小节标题。**速览只能是指针，不能复制规则本体**（复制即违反 `templates/AGENTS.md` §1「同一规则只定义一处」）。

### P15 工具与事实的真实性

**判据**：技能点名的工具、命令、字段、harness 变量、外部标准与链接真实存在。

**判法**：能核就核——`--help`、官方文档、包登记处（PyPI / npm）、规范页面。核不了写「未核实」，不得当成已核的事实来评论。

**故障模式**：编造的工具名与参数；不存在的 harness 变量或 frontmatter 字段；失效链接；把「我记得规范是这样」当成依据；引用被废弃的域名。

**改法要求**：给可复核的命令或链接；核不实的部分标注「未核实」并建议删除或改为待确认项。

## 触发实验（可执行检查）

**只对可自动触发的技能有意义**（无 `disable-model-invocation`）。手动技能的对应检查是 P8 的第二套判法，不要套用本节的矩阵。

1. 取出该技能的 `description`（只取这一段，不带正文）。
2. 从 `CHANGELOG.md` 与用户历史里挑 ≥5 条真实提问，另挑 ≥5 条明显不该触发它的提问（负样本）。
3. 逐条判断「应当触发 / 不应当触发」，填一张两列矩阵。
4. 判定：应触发未命中 → Blocker（从不触发）；不应触发命中 → Blocker（抢活）；两种都对 → 通过。

**局限必须写清**：这是静态文字匹配，不是真实 harness 空跑；本仓没有评测集与 baseline，做不到两次以上的对照运行。因此报告里要写「未做触发实验」或「仅做静态匹配矩阵」，不得把矩阵结果说成真实触发率。

## 必要时候搜索（硬规则）

判据涉及以下三类时**先查再判**，不许凭印象：

1. 提示词工程的最佳实践（指令写法、few-shot、结构化输出）；
2. Agent Skills 标准（字段、约束、渐进披露）；
3. 该 harness 的实际行为（工具能力、权限与只读模式、变量展开）。

**来源优先级**（前者为准，后者只作补充）：

1. `agentskills.io/specification`（已核可用）与同站的 `skill-creation/best-practices`（已核可用）；同站 `optimizing-descriptions`、`evaluating-skills`、`using-scripts` 用前现核。
2. 模型厂商官方 prompt engineering 指南（Anthropic / OpenAI），以官方文档站域名现查为准；旧域名会 302，核实后再写链接。
3. 该 harness 自己的官方文档（Claude Code / Codex / OpenCode / DSH）。

**报告写法**：引用给链接并标「依据来自 X」；查不到写「未核实」，不得把记忆包装成惯例，也不得虚构索引或条款号。这与 `templates/AGENTS.md` §3「禁臆造成果」、§5「检索降级」是同一套纪律——降级顺序为「换来源（换工具 / 站点 / 查询）→ 问用户」，并在回复里说明降级。

## 报告条目样例

示例中的路径为示意，不对应本仓任何现存文件。

**该报（Blocker，T1 + P9）**

> **`rules.md:24` 与 `rules.md:70`** 同一件事两个答案：`:24` 写「无配置时按官方工具默认值」，`:70` 写「无配置时按某技能的自定参数校验」，后者未声明覆写前者。依据：T1 前后矛盾；P9 例外条款未声明覆写谁，按真矛盾处理。
> 改法：`:70` 改为「按 `:24` 的配置真源」，删掉自定参数那句。

**该报（Major，T7 + P11）**

> **`SKILL.md:52-68`** 17 行的判定口径表只在一个步骤里用得到，却留在正文层（正文已 190 行）。依据：T7 层级错位（三层加载表）；P11 上下文预算（「某一步需要」的内容占比过半）。
> 改法：下沉到 `references/<name>.md`，正文改为一行「何时读」指针并标「流程第 3 步读」。

**该报（Major，P8，仅自动技能）**

> **`skills/x/SKILL.md:3`** description 只写「适用于代码审查场景」，与同仓 `y` 的「代码审查与验收」共用同一动词，无反向触发；对「帮我审这段代码」会同时命中两者。依据：P8 触发可靠性（并列命中 >1 且无优先级说明）。
> 改法：`x` 补「不用于闸门式验收，改用 `/y`」；`y` 补「不用于逐行深审，改用 `/x`」。
