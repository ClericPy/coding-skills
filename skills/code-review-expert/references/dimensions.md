# 审查维度清单

逐个维度过筛，不要跳维度。某个维度的检查项在本项目不适用时，明确说明「不适用」及其原因，不要默默跳过。

每个维度末尾附「不报」条件：命中豁免的候选问题直接丢弃或降档，不要靠数量堆出存在感。

## 一、契约、测试与环境验收

| 检查项 | 具体要求 |
| --- | --- |
| **Spec 对齐** | 改动与设计文档逐条对齐；主动清理过时文档。发现文档与代码不一致时，指出是哪一方过期并给出依据 |
| **测试覆盖** | 本次改动是否有对应测试；测试是否完备、是否**全部通过**（不得只跑部分，也不得假设通过）。除行覆盖外要求分支覆盖。agent 常对着 mock 断言或跳过边界，**测试全绿 ≠ 正确**——要核测试是否真的喂了空、`None`、0、负数、超大输入。**大量 mock 本身是依赖过复杂的信号，该动设计而不是动测试** |
| **Linter 规范** | 静态检查 / Linter 验收是否通过；本次改动后应调用 `change-linter` 技能完成 L1–L4 分级校验；未安装该技能时，按项目原生 linter 工具执行检查，并在结论中说明做了哪些、漏了哪些 |
| **依赖与锁文件** | 依赖清单与锁文件是否同步；版本是否被固定（浮动范围、快照版本、同一依赖重复声明）；新增依赖是否确有必要，脚本里用到的命令行工具是否在清单里声明 |
| **依赖与包的真实性** | 新增的 import / 方法 / 参数是否**真实存在**（核文档或实现，不靠「看着像」）；新增依赖是否是真实发布的包——幻觉出来的包名会被攻击者抢注投毒。存疑时实际跑一次，而不是只读代码 |
| **构建与 CI 配置** | 工作流权限是否最小化（写权限 + 执行 PR 提交的代码 = 不可信代码被赋权）；凭据是否走密钥通道而非明文参数；密钥是否进入构建产物、日志或部署历史 |
| **配置漂移** | 配置键是否被静默改名或删除而使旧值失效；有状态资源是否失去删除保护；同一批改动里是否只同步了一半配置 |

**不报**：缩进、行宽、引号这类 formatter 负责的格式问题；linter / 类型检查器已能可靠判定的问题（不重复报静态工具的结论）。命名与注释的**可读性**属人审范围，可按 Minor 报；注释只在「复述代码」或与代码不一致时报，不评措辞风格。

## 二、逻辑正确性

**静态工具全抓不到这一类**：linter、类型检查器、复杂度评估都过得去，代码也跑得起来，但结果是错的。这是本技能最该抓、也最容易漏的一类。

| 检查项 | 具体要求 |
| --- | --- |
| **静默错值** | 输出是否与意图一致；「看着合理」但算错的分支、默认值、聚合口径、单位换算 |
| **条件与分支** | 布尔取反、`and` / `or` 混用、`<` 与 `<=` 之差、缺失 `else` 导致落空分支、条件永真或永假 |
| **金额与时间** | 金额是否用 float（应用 `Decimal` 或整数分）；datetime 是否带时区（禁裸 `datetime.utcnow()` 与 naive 相减）；日期加减是否跨月 / 跨年正确 |
| **边界计数** | 循环与切片的起止是否差一（`range(len(x) - w)` vs `range(len(x) - w + 1)`）；分页、批次、窗口、重试次数的边界 |
| **早退与短路** | 是否漏了 `return` / `break` / `continue`；异常路径是否留下不一致的中间状态 |

**不报**：类型不符、未定义名、未使用变量这类 ruff / 类型检查器已能可靠判定的问题；「这里可能算错」「可能有并发问题」这种给不出具体行与因果链的推测。

## 三、架构与设计原则（SOLID & 务实）

| 检查项 | 具体要求 |
| --- | --- |
| **SOLID 与模式** | 是否遵循 SOLID 五大原则；是否破坏既有设计模式；是否重复造轮子（应优先复用已有实现）。SOLID 只管**已有的类**，不是「必须建类」的理由 |
| **杜绝过度设计** | 严防过度设计、假想需求（YAGNI）。为「将来可能需要」引入的抽象、配置项、扩展点，若无当下需求即视为问题 |
| **解耦与内聚** | 高内聚、松耦合；严格遵循迪米特法则，减少对象间不必要耦合；跨模块依赖方向是否正确（禁止反向依赖） |
| **副作用边界** | 纯逻辑与 IO 是否混在一处；构造函数是否碰外部系统（会向上传染给所有依赖它的类，让下游全部被迫 mock）；副作用是否收在最外层薄壳 |
| **分层归属与 Fit** | 业务逻辑是否落在正确的层（而不是塞进 CLI 层或入口脚本）；`utils` 是否成了杂物间；是否引入循环导入；是否偏离项目既有约定与模式 |

**不报**：框架生成的样板、第三方适配层、沙箱或权限声明文件——那不是设计的自由选择空间；与本次改动无关的既有架构债只记一笔，不计入本次问题。

## 四、代码质量、健壮性与并发安全

| 检查项 | 具体要求 |
| --- | --- |
| **基础与规范** | 可读性、命名清晰；杜绝冗余注释（复述代码的注释、过场注释） |
| **语义重复** | 同一逻辑换种写法重新实现，`duplicate-code` 这类字面重复检查抓不到 |
| **异常与边界** | 异常处理是否严谨、是否精准捕获；边界条件是否明确定义；是否存在裸 `except:` 吞掉异常 |
| **并发与阻塞** | 高并发安全性；**严禁阻塞协程 / 主线程**（典型如 async 函数内的同步 IO） |
| **共享可变状态** | 全局变量、缓存、实例属性是否被多个任务 / 线程写；读取后再更新的复合操作是否缺少同步 |
| **锁与死锁** | 多处加锁的获取顺序是否一致；是否在持锁期间 `await` 或执行可能阻塞的操作 |
| **资源管理** | 文件句柄、网络连接、内存等资源的生命周期是否闭环；是否存在泄漏 |
| **安全性** | 输入校验是否完备；**严禁将敏感信息（Token / 密码）写入日志**；敏感路径是否在登录与归属校验之后（缺授权检查）；TLS 校验、哈希算法等默认值是否安全（禁关闭校验、禁 MD5 / SHA-1）；`eval` / `exec` 是否被用在外部输入上 |
| **任务生命周期** | 后台任务是否超出其所有者生命周期（逃逸、无人回收）；能否被取消、能否观测到它的失败 |

**不报**：没有并发调用证据（无线程 / 进程 / 协程入口）时的竞态猜测；已被 `with` / RAII / 框架托管生命周期的句柄；调用方或类型契约已明确排除的边界输入。报注入类问题前先确认该输入**确实由外部可控**，不是可信常量；报空值问题前先回溯上游是否真会返回空。

## 五、可观测性

| 检查项 | 具体要求 |
| --- | --- |
| **杜绝废话日志** | 无意义的「进入函数」「开始处理」类日志视为问题 |
| **核心路径与异常可观测** | 核心业务路径与异常捕获处必须具备完善的日志与链路追踪点；排查问题所需的关键上下文（入参摘要、关键分支、失败原因）是否缺失 |

**不报**：日志措辞、字段顺序、格式美化；已有结构化日志的地方不再要求补装饰性日志。

## 六、性能与资源成本

报性能问题**必须先给出两项证据**：这段代码位于热路径（高频调用 / 请求链路 / 大循环内），且数据规模足以把该问题放大。缺任一项即降档，两项都缺则不报。

| 检查项 | 具体要求 |
| --- | --- |
| **N+1 与循环内 IO** | 循环体内发起查询 / 请求 / 文件读取；已有批量接口却逐条调用 |
| **复杂度与不变量** | 循环内重复计算不变量（正则编译、属性查找、重复格式转换）；反复成员判断本可用 set / dict 降到 O(1) |
| **内存放大** | 本可流式处理却整体物化；无上限缓存；一次性加载超大文件或结果集 |
| **不必要的串行** | 彼此独立的操作被串行等待；阻塞调用占着并发额度 |

**不报**：给不出数据规模与调用频次的「可能慢」；一次性脚本、启动期初始化、测试代码里的性能问题；没有基准或复杂度分析支撑的微优化；只在理论上更优、可读性代价更高的改写。

## 七、兼容性与行为变更

| 检查项 | 具体要求 |
| --- | --- |
| **向后兼容** | 线上协议与数据格式（字段编号、tag、宽度、符号性、方法名、派生 ID）是否被破坏；字段删除是否留下占位；默认值、状态码、错误语义是否被改变 |
| **迁移顺序** | 破坏性变更是否有配套迁移 / 灰发 / 回滚路径；建表、回填、双写与代码上线的先后是否自洽 |
| **契约同步** | 对外接口、消息、事件、CLI 参数、配置项的语义变化是否同步到文档与全部调用点；是否存在只改一半的调用方 |
| **旧消费方** | 已上线的旧版本客户端与旧数据是否仍能正确工作（含缺失字段、未知枚举、空值三态） |

**不报**：没有外部调用方的内部私有签名调整；尚未发布版本内部的接口打磨；与本次改动无关的历史兼容债。

## 报告前的自检

- 七个维度都过筛了吗？不适用的维度是否说明了原因？
- 是否只评了本次新增 / 修改的行？删除的代码只作上下文，未改动的代码不予评论。
- 每个变更文件（含配套的接口声明、配置、清单、文档）是否都单独过了一遍？不因它小或「次要」而跳过。
- 逻辑类结论是否给出了具体行与因果链（而不是「这里可能算错」）？是否核对过新出现的 import / 方法 / 依赖包**真实存在**？
- 每条问题是否都能定位到具体代码行或 Spec 条款？
- 性能类是否给了热路径与数据规模两项证据？兼容性类是否点明了受影响的消费方？
- 待用户确认的事项是否加粗列出，而不是替用户拍了板？
