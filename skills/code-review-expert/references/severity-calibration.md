# 三档定级锚点

定级看**后果**，不看改动大小。同一处代码在正确性与可观测性上各有一条问题，就报两条，不要合并成一条模糊描述。

## Blocker（阻塞合入）

必须满足其一：

- **正确性**：逻辑错误、边界错误、会导致错误结果的实现。
- **安全性**：输入未校验导致的注入 / 越权；敏感信息（Token / 密码）写入日志；密钥硬编码。
- **数据损坏**：不可逆的数据写入、迁移或删除缺少保护。
- **Spec 硬性违背**：与 Spec 条款直接冲突，且非文档过期所致。
- **并发致命**：协程 / 主线程被阻塞；资源泄漏在正常路径上必然发生。

## Major（应当修复）

- **架构与设计**：破坏 SOLID、反向依赖、破坏既有设计模式、重复造轮子。
- **过度设计**：为假想需求引入的抽象或配置（YAGNI）。
- **健壮性**：异常捕获过宽或吞异常；边界条件未定义；资源生命周期不闭环。
- **可观测性**：核心业务路径或异常捕获处缺少日志 / 追踪点。
- **测试**：本次改动缺少对应测试，或测试未全部通过。

## Minor（可选建议）

- **可读性**：命名不清晰、结构可简化。
- **注释**：冗余注释、注释与代码不一致、过时注释。
- **轻微重复**：无伤大雅的重复代码、可提取的命名常量。
- **不确定项**：有真实风险但证据链不完整、无法定位到具体行或 Spec 条款的怀疑 —— **必须标注不确定性**，不得伪装成结论。

## 正反例

**该报（Blocker）**

> **`api/handler.py:88`** 未校验 `user_id` 即拼接进 SQL，存在注入风险。依据：「输入校验」Spec 条款 + 该行直接字符串拼接。
> 修复：`cur.execute("SELECT * FROM t WHERE id = %s", (user_id,))`

**不该报（噪点，必须丢弃）**

> ~~「这个模块的异常处理感觉不够健壮，建议整体重构」~~
> 丢弃理由：无具体代码行、给不出证据链、无法定位到 Spec 条款。属推测，违反 ≥80% 置信度门禁。

**该报（Major，可观测性）**

> **`worker/consumer.py:57`** 消息消费失败仅 `pass`，无日志无追踪，线上故障无法定位。
> 修复：`except ParseError as exc: logger.warning("parse failed", extra={"msg_id": msg_id}, exc_info=exc)`
