按步骤执行以下流程：

1. **确定变更目标**  
   - **已有 Change**：若用户指定 Change ID，则直接使用；若未指定但存在未完成 Openspec Changes，列出供选择（含一句话需求描述）。  
   - **全新需求**：若输入与现有 Change 无关，按语义提炼需求名称并直接进入步骤 2。进入 Worktree 后创建 Spec Change，并使用 `grill-me` 交互弹窗向用户澄清模糊或冲突点，直到需求明确。

2. **建立工作环境**  
   基于当前分支的特定目录创建 Worktree，并在 Worktree 内开展后续工作（全新需求在此创建 Change）。

3. **实现变更与自测**  
   完成开发与自测，输出改动总结（改动点、改动原因）。  
   * **交互逻辑**：若用户一开始或过程中显式授权自行验收/连续执行，则直接就地自测验收，跳过等待；否则提供下方「验收模板」，**【中断等待回复】**等待用户指示或第三方评审结论。

4. **变更存档与提交准备**  
   验收通过后，将 Change 存档并清理 Openspec 变更状态。提示用户创建 Commit 或由授权智能体代为生成 Commit。  
   * **交互逻辑**：若未获完全授权，在此处**【中断等待回复】**，确认 Commit 建立完成。

5. **合并回源分支与清理**  
   确认 Commit 完成后，将 Worktree 分支以 `rebase` + `merge --ff-only` 方式合并回源分支（自动解决变基冲突，严禁产生合并提交）。合并完成后清理 Worktree。

---

**验收模板**  
包含：当前变更名称、Worktree 名称、完成进度、大致需求、原分支名称。  
评审维度：文档对齐情况、测试覆盖与通过率、逻辑合理无异味、L4 Lint 验证。  
要求：  
- 仅输出 Markdown 格式评审结论。  
- 发现明显 Bug 或待确认事项仅作记录，不作修改；评审者绝不修改代码或创建 Commit。

**合并模板**  
包含：当前 Worktree 名称、源分支名称。  
要求：仅使用 `rebase` + `merge --ff-only`，不允许产生合并提交，自动解决变基冲突。
